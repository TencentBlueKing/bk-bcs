# size 规模评分标准（story / bug 共用）

本文档定义 TAPD 工作项 `size` 字段的取值口径：**size 表示完成工作项所需的相对实现规模/工作量**，
数值越高代表规模越大，采用斐波那契数列（1、2、3、5、8、13…）取值。本标准由
`tapd-story-score`（需求）与 `tapd-bug-evaluation`（缺陷）**共用**，保证 story 与 bug
两侧的 size 语义完全一致。

---

## 〇、字段定义：size（规模）与 business_value（业务价值）

| | **size（规模）** | **business_value（业务价值）** |
|---|---|---|
| **定义** | 工作项的**相对实现规模/工作量**度量——"做多大" | 工作项对**用户和业务的价值**度量——"值不值得做" |
| **决定因素** | 5 个实现规模维度：实现范围、技术复杂度、依赖、风险、验证成本 | RICE 模型 4 个参数：Reach（触达用户量）、Impact（影响程度）、Confidence（信心指数）、Effort（开发人天） |
| **取值方式** | 各维度评 1–5 分 → maxDim 锚定 + avgDim 校准 → 斐波那契数列（1/2/3/5/8/13…） | RICE 公式：(Reach × Impact × Confidence) / Effort → 整数综合分 |
| **TAPD 字段** | `size`（integer） | `business_value`（integer，仅 story 支持） |
| **适用范围** | story 和 bug 均适用 | 仅 story 适用；bug 无此字段 |
| **评分标准文档** | 本文档 | `rice-scoring-standard.md` |

**核心不变量**：两个字段完全解耦、互不赋值。
- size 仅由相对实现规模决定，**不含任何价值/用户影响维度**（Reach、Impact、Confidence、影响范围/用户群体/业务覆盖面）。
- business_value 仅由 RICE 模型决定，**不含任何实现规模维度**。
- size 大 ≠ 业务价值高（可能工作量大但不重要）；business_value 高 ≠ size 大（可能工作量小但很紧急）。

---

## 一、5 个规模维度（复用现有 PERT 基线维度，不新增独立故事点体系）

size 的规模维度直接**复用**现有 PERT 方法与基线所覆盖的维度，不引入独立故事点体系。
story 的来源为 `../tapd-story-score/references/story-effort-baseline.md`，
bug 的来源为 `../../tapd-bug-evaluation/references/odc-effort-baseline.md`。

| 规模维度 | 含义 | story PERT 来源 | bug PERT 来源 |
|----------|------|-----------------|---------------|
| 实现范围 | 改动/操作/内容涉及的文件、模块、资源数量 | 工时基线表（纯 UI / 单模块 / 跨模块 / 集成 / 架构） | ODC 基线区间（改动集中度） |
| 技术复杂度 | 算法、时序、新技术栈等技术难度 | 调整因子"技术难度高（+40%）"、算法/时序基线 | ODC 类型（算法/时序）、"跨模块（+50%）" |
| 依赖 | 跨团队、跨模块、第三方、历史接口兼容 | 调整因子"跨团队协作（+50%）"、"兼容历史接口（+30%）" | "跨模块（+50%）"、"涉及第三方（+40%）" |
| 风险 | 数据迁移、回归、可用性/数据/安全风险、悲观点 P | 调整因子"数据迁移（+30%）"、悲观点 P | 回归风险、P（根因偏差/关联影响/重构） |
| 验证成本 | 测试覆盖、验证复杂度、CR 工时 | 调整因子"已有完善测试（-20%）"、CR 工时 | 测试难度、"完善单测（-20%）" |

> 上述维度均来自现有 PERT 基线已覆盖的因素，仅将其"从 M 值调整因子"复用为"难度打分依据"，
> **不新增维度体系、不引入独立故事点**（满足 FR3）。

## 二、各维度 1–5 分评分标尺

对每个规模维度独立评 1–5 分：

### 实现范围

| 分值 | 描述 |
|------|------|
| 1 | 单点/单文件，改动集中，边界清晰 |
| 2 | 单一函数/方法或少量文件改动 |
| 3 | 单一模块内多处改动 |
| 4 | 涉及 2 个及以上模块的协同改动 |
| 5 | 跨多模块/多文件重构或架构级调整 |

### 技术复杂度

| 分值 | 描述 |
|------|------|
| 1 | 无算法/无技术难点，直接实现 |
| 2 | 常规业务逻辑，团队有成熟经验 |
| 3 | 含一定逻辑分支或数据处理复杂度 |
| 4 | 涉及复杂算法/较难的数据结构或协议 |
| 5 | 并发/时序/新技术栈等高难度，团队无现成经验 |

### 依赖

| 分值 | 描述 |
|------|------|
| 1 | 完全独立，无外部依赖 |
| 2 | 依赖单一内部模块，接口稳定 |
| 3 | 依赖多个内部模块或需兼容历史接口 |
| 4 | 跨团队协作或涉及第三方服务 |
| 5 | 强跨团队/多第三方依赖，需等待外部排期 |

### 风险

| 分值 | 描述 |
|------|------|
| 1 | 改动完全隔离，无回归/数据/可用性风险 |
| 2 | 影响面小，风险可控 |
| 3 | 需处理一定回归范围或存量数据 |
| 4 | 涉及数据迁移或核心链路，回归范围大 |
| 5 | 影响核心框架/数据模型，回归与可用性风险极高 |

### 验证成本

| 分值 | 描述 |
|------|------|
| 1 | 有完善自动化测试，直接运行验证 |
| 2 | 有部分自动化，需少量手工验证 |
| 3 | 需中等量手工测试，场景较多 |
| 4 | 需大量手工测试，验证复杂难自动化 |
| 5 | 极难验证，需特殊环境/压测/时序模拟 |

## 三、规模评分 → 斐波那契 size 映射

统一采用 **"最大维度锚定 + 平均校准" 两步法**（story/bug 共用，避免加权引入隐性权重歧义）：

1. 对 5 个规模维度各评 1–5 分。
2. 取 `maxDim = 5 维度最大值`、`avgDim = 5 维度算术平均`。
3. 先由 `maxDim` 锚定斐波那契档位（单点最大规模维度决定量级），再由 `avgDim` 在相邻档间校准。

| maxDim | avgDim 条件 | size（斐波那契） | 含义 |
|--------|-------------|------------------|------|
| 1 | — | 1 | 极小规模改动，单点定位 |
| 2 | avg < 2.0 | 1 | 小规模改动 |
| 2 | avg ≥ 2.0 | 2 | 小规模改动（偏多点） |
| 3 | avg < 2.6 | 2 | 中小规模 |
| 3 | avg ≥ 2.6 | 3 | 中等规模改动 |
| 4 | avg < 3.4 | 3 | 中大规模改动 |
| 4 | avg ≥ 3.4 | 5 | 较大规模改动 |
| 5 | avg < 4.2 | 5 | 较大规模改动（单维度评分高） |
| 5 | 4.2 ≤ avg < 4.6 | 8 | 大规模改动，**建议评估拆分** |
| 5 | avg ≥ 4.6 | 13 | 极大规模改动，**必须拆分** |

> `avg ≥ 4.6` 表示五个维度中至少三个为 5 分、其余不低于 4 分的广泛高复杂度工作项；
> 因而 13 有明确、可复算的进入条件，而不是由未定义的“组合评估结果”推断。

---

## 四、size ≤5 建议、拆分约束与团队可自定义说明

- 常规单工作项 size 建议 **≤5**；size = 8 提示“建议评估拆分”，size ≥13 为“必须拆分”。
- **story 侧**：单子需求预估工时 ≤24 人时（3 人天）是独立强约束，见
  `requirement-splitting-guide.md`（§4 / §9）。工时 >24 人时或 size ≥13 任一成立，
  主 skill 均必须回拨重拆；size = 8 且工时合格时仅保留建议标记。
- **bug 侧**：size ≥8 提示按 ODC 子问题拆分或专项处理。
- **团队可自定义**：上表阈值为默认基线，允许团队在本标准文档中按历史数据自定义
  maxDim/avgDim 边界与斐波那契档位映射；核心不变量始终不变——
  **size 仅由 5 个规模维度决定，不含任何价值/用户影响维度**。

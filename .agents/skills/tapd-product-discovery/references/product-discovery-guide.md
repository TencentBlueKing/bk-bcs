# 产品调研与 PRD 整理指南

`tapd-product-discovery` 在产品前期使用这份清单，把想法、反馈或业务问题整理成能评审、能拆单、能交给研发继续处理的产品文档。

## 1. 信息收集

先补齐这些信息：

| 项目 | 说明 |
|------|------|
| 需求来源 | 老板要求、用户反馈、数据异常、竞品观察、内部效率问题等 |
| 目标用户 | 谁会直接使用，谁会受影响 |
| 当前问题 | 用户现在怎么做，哪里慢、错、贵、难维护 |
| 业务价值 | 做完后解决什么问题，用什么指标判断有效 |
| 范围边界 | 这次做什么，不做什么 |
| 约束条件 | 时间、人力、合规、架构、前后端能力、数据来源 |

信息不完整时，不要直接写“待确认”结束。先给出最多 8 个关键问题，按“先回答”和“可后补”分组。

## 2. 调研内容

按需求复杂度选择调研深度。

### 轻量需求

适用于文案、配置、小交互、已有能力小幅调整：

- 需求来源
- 目标用户
- 当前问题
- 期望结果
- 验收标准

### 标准需求

适用于新增页面、流程调整、跨前后端改造：

- 用户场景
- 用户路径
- 竞品或替代方案
- 项目内已有能力
- 原型或流程图
- 成功指标
- 风险和非目标

### 复杂需求

适用于影响多个角色、多个系统或上线风险较高的需求：

- 用户访谈或样本反馈
- 竞品对照表
- 数据现状
- 多方案比较
- 角色影响分析
- 分阶段交付建议
- 设计、前端、后端拆单建议

## 3. PRD 需要回答的问题

PRD 不求长，下面几件事要说清楚：

- 为什么要做
- 给谁用
- 用户怎么用
- 做到什么程度算完成
- 哪些情况不管
- 需要哪些设计、前端、后端工作
- 上线后怎么判断有效

## 4. 评审前检查

进入 `for approve` 前检查：

- [ ] 需求来源清楚
- [ ] 目标用户清楚
- [ ] 核心场景清楚
- [ ] 产品范围清楚
- [ ] 验收标准可验证
- [ ] 非目标已写明
- [ ] 需要拆哪些角色子单已有判断
- [ ] 关键风险已写明

未通过检查时，保持产品父单在 `doing`。

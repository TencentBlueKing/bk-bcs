# 角色子单拆分规则

产品父单通过评审后，按本规则判断是否创建设计、前端、后端子单。

## 1. 总原则

- 产品父单总是存在。
- 子单只按实际工作创建，不强制三种角色都创建。
- 子单要挂在产品父单下。
- 子单描述只写该角色需要完成的工作，不重复整篇 PRD。
- 未创建的角色要在产品父单中写明原因。
- 原型评审结果会影响拆单判断。原型需要交互或视觉细化时创建设计子单；原型包含页面、表单、状态处理时创建前端子单；原型依赖接口、数据、权限或状态机时创建后端子单。

## 2. 创建条件

### 设计子单

满足任一条件就创建：

- 新增或调整用户流程
- 新增页面、弹窗、表单、图表、空态、异常态
- 需要交互说明、视觉稿、原型或设计评审
- 影响信息架构或导航结构
- 需要与前端确认组件使用方式

可以跳过：

- 纯后端能力
- 纯配置或脚本任务
- 只改已有文案且不影响布局
- 已有设计稿可直接复用，且产品父单中写清楚链接

### 前端子单

满足任一条件就创建：

- 新增或调整页面、组件、路由、表单、校验、图表
- 需要前端状态管理、接口联调、权限展示、埋点
- 需要处理加载态、空态、错误态、响应式或浏览器兼容
- 需要根据设计稿还原 UI

可以跳过：

- 纯后端接口、任务或数据处理
- 只改服务端配置
- 前端无展示或交互变化

### 后端子单

满足任一条件就创建：

- 新增或调整接口、数据模型、权限、状态机
- 需要后台任务、消息、缓存、审计日志、限流
- 需要对接外部系统
- 需要数据迁移或历史数据修复
- 前端依赖新的服务端能力

可以跳过：

- 纯静态页面
- 纯样式调整
- 前端本地逻辑即可完成
- 只调整产品文案或帮助说明

## 3. 子单描述结构

```markdown
# <角色>子需求：<需求名称>

## 父需求

- 产品父单：<ID / 链接>
- 产品文档：<路径或链接>

## 本角色目标

<说明该角色要交付什么。>

## 工作范围

### 包含

- <工作项 1>
- <工作项 2>

### 不包含

- <这次不做的内容>

## 输入材料

- PRD：<链接或路径>
- 页面原型 Spec：<路径或链接，若无写“不需要：原因”>
- HTML 原型：<路径或链接，若无写“不需要：原因”>
- 原型/设计稿：<链接或路径，若无写“不需要：原因”>
- 接口/数据说明：<链接或路径，若无写“待研发澄清”>

## 验收标准

- <需要...>
- <完成后可以...>

## 依赖

- <依赖其他角色子单或外部系统；没有则写“无”>
```

## 4. 默认状态

创建子单时统一使用 `backlog`。

后续由各角色流程推进：

| 角色 | 后续状态 |
|------|----------|
| 设计 | `backlog -> todo(已规划) -> designing -> design approved -> done` |
| 前端 | `backlog -> for approve -> approved -> todo(已规划) -> doing -> for test -> tested -> for gray -> grayed -> done` |
| 后端 | `backlog -> for approve -> approved -> todo(已规划) -> doing -> for test -> tested -> for gray -> grayed -> done` |

## 5. 父单结束条件

产品父单可以进入 `done` 的条件：

- PRD 或产品方案已通过评审。
- 需要的角色子单已创建。
- 不需要创建的角色已写明原因。
- 子单链接已回写到产品父单。

产品父单 `done` 不表示功能上线。上线状态由前端/后端子单继续记录。

# BKUI HTML 原型生成规范

## 使用时机

在 PRD 完成并产出页面原型 Spec 后、角色拆单前使用本规范生成静态 HTML 原型。页面原型生成以本仓参考文件为执行依据，沉淀产品前置流程需要的 BKUI 原型规则。

## 输入材料

- PRD：产品目标、用户场景、范围、验收标准。
- 页面原型 Spec：页面结构、字段、操作、状态、Mock 数据。
- 现有产品页面：导航层级、组件密度、命名和交互习惯。
- 约束说明：权限、数据来源、浏览器兼容、评审截止时间。

## 输出路径

建议输出到当前需求工作目录：

- 单页原型：`workflows/issue-<iid>/prototype/index.html`
- 多页原型：`workflows/issue-<iid>/prototype/<页面名>.html`
- 静态资源：`workflows/issue-<iid>/prototype/assets/`

HTML 文件应可直接用浏览器打开预览，不依赖构建流程。样式和轻量交互可以内联，也可以引用同目录静态资源。

## 页面类型与布局

- 列表页：导航区、筛选区、主操作区、表格区、分页区。
- 表单页：标题区、分组表单、底部操作区、校验提示。
- 详情页：摘要信息、分组详情、关联列表、操作入口。
- 配置页：左侧分类或顶部标签、配置表单、保存反馈。
- 流程页：步骤条、当前任务区、辅助说明、提交确认。

布局应保持业务工具的清晰密度：信息层级明确，主操作靠近主内容，评审人无需滚动过多页面即可理解核心流程。

## BKUI 组件约束

- `bk-navigation`：用于表达产品导航、侧边栏、顶部栏和当前位置。
- `bk-table`：用于列表、关联资源、操作记录等结构化数据展示。
- `bk-button`：用于主操作、次操作、危险操作和表格行操作。
- `bk-form`：用于新增、编辑、筛选、配置等表单结构。
- `bk-dialog`：用于确认、二次提醒、轻量编辑或短流程反馈。
- `bk-sideslider`：用于详情查看、复杂编辑、不中断列表上下文的侧滑操作。

静态 HTML 可以用 BKUI 组件名、类名或清晰的 DOM 结构表达组件语义；重点是让评审人能看懂页面层级、字段、操作和状态。

## HTML 预览要求

- 原型必须是浏览器可打开的静态 HTML 文件。
- 首屏展示完整主流程入口和关键页面信号。
- 页面宽度、表格列宽、按钮区域和弹窗/抽屉尺寸要稳定，避免文字溢出或重叠。
- 多页面原型应提供可点击的页面入口或导航链接。
- 需要评审的弹窗、抽屉、空态、错误态可以用页面内示例区或交互按钮触发。

## Mock 数据要求

- 使用贴近业务的 Mock 数据，不使用无意义的 `foo`、`test`、`123` 作为主要内容。
- 覆盖正常数据、长文本、空值、异常状态和权限差异。
- 表格默认展示 5-10 条数据，并包含分页、筛选结果数量或总数提示。
- 表单默认值、占位文案、校验错误文案要与 PRD 和页面原型 Spec 保持一致。

## 状态与交互要求

- 加载态：表格 loading、按钮提交中、局部区域加载。
- 空态：无数据文案、引导操作、清空筛选后的恢复入口。
- 错误态：接口失败、权限不足、保存失败、删除失败。
- 成功态：保存、提交、删除、批量操作后的反馈提示。
- 禁用态：按钮或表单不可操作时说明原因。
- 交互说明：新增、编辑、删除、批量操作、打开 `bk-dialog`、打开 `bk-sideslider` 等关键动作要能在原型中被评审。

## 原型评审输出

评审后在产品工作目录记录：

- 原型 HTML 路径。
- 评审结论：通过 / 需调整。
- 调整项：问题、负责人、截止时间。
- 对角色拆单的影响：是否需要设计子单、前端子单、后端子单，以及原因。

## 不适用场景

- 已有成熟设计稿且无需补充页面原型。
- 纯后端能力、数据修复、脚本任务或无可视化交互的需求。
- 只调整文案、权限配置或已有页面的轻量参数，且 PRD 已能直接支撑拆单。
- 需要高保真视觉稿、复杂动画或真实接口联调时，应进入对应设计或研发流程。

## 总体原则

### 环境设计优先于模型优化

当 Agent 表现不佳时，遵循以下排查顺序：

1. **先检查工具**：Agent 是否具备完成任务所需的工具？
2. **再检查上下文**：Agent 是否能获取到足够的信息？
3. **然后检查约束**：是否有明确的规则告诉 Agent 什么该做、什么不该做？
4. **最后考虑模型**：确认以上都没问题后，才考虑模型能力是否足够。

LangChain 的实验验证了这一原则：未更换模型，仅通过优化 Harness，Agent 在
SWE-bench 的排名从 Top30 提升至 Top5。

### 渐进式复杂度

- 从最简单的 Harness 开始，根据实际问题逐步增加约束
- 避免一开始就构建过度复杂的系统
- 每增加一个约束，都应有明确的问题驱动

### 可观测优先

- 在优化性能之前，先确保能看到 Agent 在做什么
- Trace 数据是诊断问题的基础，优先建设可观测性

## 上下文工程最佳实践

### 知识管理

**做法 1：版本控制的文档即唯一来源**

将所有 Agent 需要的知识存入 git 仓库的 `docs/` 目录，避免依赖外部 Wiki
或即时通讯记录。这样做的好处：
- 文档与代码同步演进，减少不一致风险
- PR Review 时可以检查文档是否同步更新
- 新 Agent（或新团队成员）只需要 clone 仓库就能获取全部上下文

**做法 2：AGENTS.md 作为入口**

AGENTS.md 是入口：harness 短头（概述、关键、门闩）保持精简；
若仓内已有项目记忆（硬约束、任务路由、交付法、验证命令等），
按 `references/agents-merge.md` **先理解再裁决**后保留在入口，
**不**为凑行数整文件冲掉。详细规范下沉 `docs/harness/` / `docs/standards/`。

Agent 通过 AGENTS.md 了解全局，按需深入具体文档，
避免大量信息一次性塞入上下文窗口。

### 上下文效率

**做法 3：上下文窗口即稀缺资源**

大模型的上下文窗口虽然在扩大，但仍然是有限资源。最佳实践：
- 与当前任务相关的信息优先加载
- 大文件通过目录/索引定位到相关段落，避免全量加载
- 历史对话及时压缩或归档，释放上下文空间

**做法 4：结构化高于自由文本**

Agent 理解结构化文档（Markdown 表格、YAML 配置、JSON Schema）
的效率远高于自由文本。规范文档应优先使用结构化格式。

## 架构约束最佳实践

### 刚性约束

**做法 5：通过代码强制约束，而非靠 Prompt 提醒**

将架构规则实现为 Linter 规则或结构测试，在 CI 中自动检查。
靠 Prompt 提醒"请不要在 domain 层引用 infrastructure 层"是不可靠的——
Agent 在复杂任务中容易遗忘 Prompt 中的约束。

**做法 6：错误信息即修复指南**

Linter 的错误信息应该告诉 Agent 怎么修，而不只是说哪里错了：
- 差：`ARCH-001: 违反依赖规则`
- 好：`ARCH-001: domain/user.go 引用了 infrastructure/database.go。修复方式：在 application/ 层定义 UserRepository 接口`

这样 Agent 可以自主修复，无需人工介入。

### 灵活约束

**做法 7：ADR 记录架构决策的"为什么"**

架构决策记录（Architecture Decision Record）不仅记录"选了什么方案"，
更重要的是记录"为什么选这个方案""考虑过哪些替代方案"。
Agent 遇到类似问题时，可以参考历史决策的推理过程，做出一致的决策。

**做法 8：Parse, Don't Validate 减少错误传播**

在数据进入系统的边界处一次性解析为强类型，后续代码只处理"已知有效"的数据。
这比在每一层都做验证更高效，也减少了"验证遗漏"导致的错误。

## 熵管理最佳实践

### 自动化检测

**做法 9：文档园艺 Agent**

部署后台 Agent 定期扫描文档与代码的一致性：
- 文档中引用的文件路径是否存在？
- 文档中描述的 API 接口是否与实际代码一致？
- 文档中的架构图是否反映了当前架构？

OpenAI 的实践：文档园艺 Agent 发现不一致时自动提交修复 PR，
简单修改直接合并，复杂修改通知人类 Review。

**做法 10：架构违规检测集成到 CI**

在 PR 流程中自动检查架构违规，确保问题在合入前被发现：
- 依赖方向违规 → 阻断合并
- 新增循环依赖 → 阻断合并
- 死代码 → 警告但不阻断

### 技术债管理

**做法 11：技术债可视化**

定期生成技术债报告，让团队清晰看到"债务"水平：
- 按类型分类（架构违规、死代码、过时文档、TODO 堆积）
- 标注优先级（阻塞性 > 影响效率 > 代码美观）
- 追踪趋势（是在增长还是在收敛？）

**做法 12：设定技术债"红线"**

当技术债超过阈值时，暂停新功能开发，集中清理。
这个阈值需要团队商定，常见策略：
- 总债务不超过 N 条
- 每迭代新增不超过 M 条
- 每迭代必须清理 K 条

## 工具能力最佳实践

### 接口设计

**做法 13：统一工具接口协议**

所有工具遵循相同的输入/输出格式，降低 Agent 的学习成本：
- 输入：结构化参数（JSON），区分必填和可选
- 输出：统一的 `{success, data, error}` 结构
- 错误：明确的错误码 + 可读的错误信息

**做法 14：一个工具只做一件事**

遵循"关注点分离"原则，每个工具的功能边界清晰：
- 差：`file_manager(action, path, content)` — 一个工具做读写删查
- 好：`read_file(path)`、`write_file(path, content)`、`delete_file(path)` — 各司其职

### 稳定性保障

**做法 15：沙盒执行防止破坏**

Agent 的工具调用应在沙盒环境中执行：
- 文件操作限制在项目目录内
- 网络访问限制到白名单域名
- 禁止访问系统敏感路径
- 危险操作需要人工确认

**做法 16：超时-重试-幂等三件套**

所有外部调用都需要配置：
- **超时**：避免 Agent 因等待而卡住
- **重试**：临时性故障自动恢复（指数退避，最多 3 次）
- **幂等**：重试不会产生副作用（如重复创建资源）

## 执行与验证最佳实践

### 执行循环

**做法 17：Agent Loop 是核心**

"观察-推理-行动-验证"的循环是 Agent 可靠执行的基础：
```
while not finished:
    observation = observe(environment)
    thought = reason(observation, task_spec)
    action = plan(thought)
    result = execute(action)
    update_state(result)
    if verify(result, task_spec):
        mark_complete()
```

没有验证环节的循环是危险的——Agent 可能"做了但没做对"而自己不知道。

**做法 18：循环保护防止失控**

设置多层保护机制：
- 最大循环次数限制（防止无限循环）
- 最大执行时间限制（防止 Token 浪费）
- 无进展检测（连续 N 次状态无变化则暂停）

### 验证机制

**做法 19：预完成检查清单**

参考 LangChain 的 `PreCompletionChecklistMiddleware`，在 Agent 宣称完成前
强制执行检查清单：
- 是否运行了测试？
- 是否对照了任务 Spec 逐条检查？
- 是否更新了受影响的文档？
- 是否有未处理的 Linter 错误？

Agent 不能跳过检查清单直接宣称完成。

**做法 20：验证失败即重新执行**

验证发现问题后，自动回到执行循环修复，而非简单报错退出。
但需要设置最大修复次数，超过后请求人工介入。

### 可观测性

**做法 21：记录每一步操作**

Agent 的执行日志应包含：
- 每个工具调用的输入和输出
- 推理过程的关键节点
- Token 消耗和耗时数据
- 任务状态变迁

这些日志是诊断问题的基础。

**做法 22：Trace 分析驱动优化**

通过分析 Trace 数据发现 Harness 的改进点：
- Agent 在哪一步消耗了最多 Token？（可能需要优化 Prompt）
- 哪些工具调用经常失败？（可能需要加强稳定性）
- Agent 是否有重复劳动？（可能需要增加缓存或模板）
- 任务在哪一步最容易漂移？（可能需要加强约束）

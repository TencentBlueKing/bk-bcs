# 依赖识别与 DAG 构建规则

本文档说明在迭代规划中如何从需求描述里识别依赖关系、构建有向无环图（DAG），
以及在 DAG 上确定入迭代顺序的具体规则。

## 一、为什么需要依赖分析

需求之间往往存在"必须先做完 A 才能做 B"的依赖关系。如果规划时忽略依赖：

- 高 size 需求被先排进迭代，但其前置依赖在下个迭代，导致开发被卡住
- 部分子模块开发完成但缺少底层能力支撑，验收无法闭环
- 跨模块联调被推迟，集成风险后置

因此规划时需要扫描每个候选需求 `description` 中的依赖说明，自动扩展规划范围
并按依赖顺序排列。

## 二、依赖来源识别

### 2.1 标准依赖章节

由 `tapd-story-clarification` 与 `tapd-story-evaluation` 输出的规范需求文档中，
通常会有"依赖关系"章节。常见的章节标题包括：

- `## 依赖关系`
- `## 依赖`
- `## 前置依赖`
- `## Dependencies`
- `## 依赖需求`

### 2.2 依赖描述格式

章节内容可能采用以下格式之一：

**列表式**：
```markdown
## 依赖关系
- 依赖需求 1070204916133520274（成员管理前端页面功能完善）
- 依赖需求 1070204916133520265
```

**表格式**：
```markdown
## 依赖关系
| 需求 ID | 名称 | 依赖类型 |
|---------|------|---------|
| 1070204916133520274 | 成员管理前端页面 | 前置依赖 |
```

**链接式**：
```markdown
## 依赖关系
- https://example.com/tapd_fe/{workspace_id}/story/detail/1070204916133520274
```

**纯文本式**：
```markdown
## 依赖关系
本需求需要先完成成员管理后台开发（#1070204916133520274）。
```

### 2.3 ID 提取规则

从依赖描述中提取 19 位长 ID 或短 ID：

- 优先识别**连续 19 位数字**作为长 ID
- 其次识别 `#数字` 或 `story/detail/数字` 中的数字
- 提取出的短 ID 后续使用 TAPD MCP `tapd_id_get` 转换为长 ID

### 2.4 不作为依赖处理的情况

- 仅出现在需求描述正文（非"依赖关系"章节）的需求 ID 引用
- 标注为"参考"、"相关"、"对比"的需求引用
- 已经处于"已发布"或"已完成"状态的需求

## 三、DAG 构建

### 3.1 节点与边

- **节点**：候选需求列表 `eval_list` 中的所有需求 ID
- **边**：需求 A 依赖需求 B 时，建立 `B → A` 的有向边（B 必须先于 A）

### 3.2 依赖扩展

对 `eval_list` 中每个需求识别出的依赖 ID：

| 依赖需求状态 | 处理方式 |
|--------------|---------|
| `v_status="approved"` 且 `iteration_id=""` 且 `children_id="|"` | 加入 `eval_list`，建立依赖边 |
| 已在 `eval_list` 中 | 仅建立依赖边 |
| 已入其他迭代 | 不加入 `eval_list`，记录为"外部依赖已被规划" |
| 状态为"已澄清"或更早 | 不加入 `eval_list`，记录为"外部依赖未评估"，告知用户 |
| ID 不存在 | 跳过，记录警告 |

### 3.3 循环依赖检测

构建 DAG 时检测循环。如发现循环：

- 列出涉及循环的需求 ID 链路
- 告知用户该循环存在，建议人工介入调整
- 在规划时按 size 降序兜底处理（不强制依赖顺序）

## 四、排序规则

完成 DAG 构建后，按以下三层规则确定入迭代顺序：

### 4.1 第一层：拓扑排序

执行 Kahn 算法或 DFS 拓扑排序，得到拓扑序列。**被依赖的需求（入度为 0）排在前面**。

### 4.2 第二层：同层 size 降序

同一拓扑层级内（即彼此无依赖关系的需求），按 `size` 字段降序排列。

**理由**：高 size 需求工作量更大，越早进入迭代，开发时间越充裕；同时 size 高
往往意味着价值更高。

### 4.3 第三层：优先级兜底

`size` 相等时，按优先级降序：

| priority_label | 排序权重 |
|----------------|---------|
| High | 3 |
| Middle | 2 |
| Low | 1 |
| 缺省 | 0 |

## 五、入迭代决策

按排序后的列表 `ordered_list` 顺序遍历，每个需求按以下规则决定是否入迭代：

```
若 当前需求.size <= 剩余 total_size:
    入迭代，total_size -= 当前需求.size
否则:
    跳过当前需求，尝试下一个（可能存在更小的需求能塞入）
```

遍历完成后，所有未入迭代的需求记录到"未规划需求"列表，作为汇总输出的一部分。

## 六、调试建议

如果规划结果不符合预期，按以下顺序排查：

1. 检查需求 description 中"依赖关系"章节格式是否规范
2. 检查依赖的需求 ID 是否正确（短 ID vs 长 ID）
3. 检查依赖需求的 v_status 是否为"approved"
4. 检查 size 字段是否填写（缺失时按 0 处理，会被排到最后）
5. 检查是否存在循环依赖（控制台会有警告）

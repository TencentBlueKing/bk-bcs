# Definition of Ready 清单（回写前门禁）

本清单是 `tapd-story-clarification` 在 **回写 TAPD 并推进状态为 `approved`** 前的
强制门禁。目的是保证移交给下一流程（迭代规划 / 技术规范）的需求满足"规范化、
信息清晰、可执行、可落地、可评估"。

## 使用规则

- Agent 在展示需求文档给用户确认**之前**，先按本清单自检
- **任一项未通过 → 不允许 `v_status: approved`**：
  - 仍可回写 `description`（保留最新澄清结果）
  - 状态保持 `backlog`
  - 在最终汇总输出中标注未通过项，交由用户后续补齐
- Skip 场景（纯文案 / 配置变更）同样需要走本清单，只是多数项可以简单标注 N/A

## 清单（8 项，均为二值判断）

- [ ] **1. 业务目标已量化**
  - 至少包含一个可测量的数字指标（如"P99 < 200ms"、"MTTR 从 45min 降至 20min"、"日活提升 5%"）
  - 禁止只写"提升体验 / 优化性能"

- [ ] **2. Actor 明确**
  - 受影响的角色 / 系统 / 岗位已具体到人物角色或子系统名称
  - 禁止使用"用户 / 管理员"这类空泛描述而不做限定

- [ ] **3. Scope In / Out 显式声明**
  - `边界范围 → 本期包含` 与 `本期不包含` 两节均已填写
  - "本期不包含"至少写清 1 条以防范围蔓延（无边界风险时可写"暂无"并说明理由）

- [ ] **4. 每条业务规则至少 1 正例 + 1 反例**
  - 每条列在 `业务规则` 中的规则，都能在 `验收标准` 中找到对应的正例（happy path）与反例（unhappy / 边界）
  - 采用 Given-When-Then 表达（见 `clarification-guide.md` §四 与 §BDD 反模式）

- [ ] **5. 主流程 + 至少 1 条异常流程覆盖**
  - 功能需求 / 验收标准共同覆盖了正常路径与至少一条异常路径
  - 例如：接口调用失败、超时、权限不足、参数校验失败等

- [ ] **6. 非功能需求量化且绑定测量方法**
  - 每条性能 / 安全 / 可用性指标都给出：**数值 + 测量场景 + 测量方式**
  - 例："P99 响应时间 < 200ms（100 并发压测环境，使用 wrk 测量）"

- [ ] **7. 无 🔴 阻塞性未决问题**
  - `假设与未决问题 → 未决问题` 中不存在标记为阻塞级别的项
  - 非阻塞（🟡）问题允许存在，需明确"待谁确认 / 建议 Deadline"

- [ ] **8. 假设章节已显式声明**
  - `假设与未决问题 → 假设` 已填写；如无任何假设，也必须显式写"无"，禁止空缺
  - 每条假设需附"若不成立影响的 AC / 范围"

## 反模式提醒

- 不要为了通过清单而机械填空（如"性能：无要求"、"边界：无"）
- 若某项确实 N/A，请**说明理由**，让下一流程的评审者能理解
- 清单不是替代思考，而是**兜底防漏**

# 熵管理（Entropy Management）

> 目标：让系统"保持整洁"——通过自动化机制控制系统熵增速度，确保长期可维护。

## 1. 文档园艺机制

### 1.1 自动一致性检测

| 检测项 | 频率 | 方式 | 责任人 |
|-------|------|------|-------|
| harness / standards 与代码是否漂移 | 规范变更后或用户触发「文档巡检」 | harness-gardening | Agent + 模块 Owner |
| 文档引用的文件路径是否存在 | 每次 PR | Review + 可选 CI | 提交者 |
| 工作单元 AGENTS 是否被根索引 | 园艺全量扫描 | gardening 维度 12 | harness 维护者 |
| API / proto 与文档是否一致 | 接口变更时 | 对照 `docs/apidoc`、`docs/openapi`、服务 proto | 服务 Owner |
| 特性设计是否归档 | 新功能合入前 | CONTRIBUTING：设计文档进 `docs/features/` | 提交者 |

### 1.2 园艺流程

1. 检测到不一致 → 在巡检报告中按 P0/P1 列出
2. 简单不一致（断链、索引缺失、预设漂移）→ Agent 修复 harness 文档
3. 复杂不一致（架构叙述过时）→ 通知模块 Owner，不擅自改工作单元 `AGENTS.md` 正文
4. `docs/standards/` 以预设库为权威，禁止在接入仓手工改预设正文
5. `docs/business-standards/` **永不**被园艺覆写

## 2. 架构违规检测

### 2.1 检测策略

| 检测类型 | 触发时机 | 工具 | 阻断级别 |
|---------|---------|------|---------|
| Go 风格 / 复杂度 | PR 前提交者本地 | golangci-lint（见 commit-spec） | 警告；组件若有 CI 则随组件 |
| 生成物被手改 | Review | git diff + 工作单元 AGENTS 禁令 | 阻断合入 |
| 跨服务 internal 引用 | Review | 人工 / 后续可加 import 检查 | 阻断合入 |
| 死代码 / 未使用导入 | PR | 语言 Linter | 警告 |

仓库根 `Makefile` 的 `test` 目标目前只覆盖部分服务；**不得**把「跑了根 `make test`」说成全仓验证通过。

### 2.2 违规处理流程

- **阻断级别**：PR 无法合并，必须先修复
- **警告级别**：允许合并，但记入技术债
- **报告级别**：仅记录，定期批量处理

## 3. 技术债追踪

### 3.1 追踪机制

| 债务类型 | 识别方式 | 记录位置 | 清理策略 |
|---------|---------|---------|---------|
| 过时文档 | 园艺扫描 | Issue 或 PR 说明 | 发现即修简单项 |
| TODO/FIXME | 代码扫描 | 组件 Issue | 每迭代 Review |
| 根测试覆盖不全 | `Makefile` `test` 目标范围 | 本文 | 改哪测哪，不假装全仓绿 |
| 组件 harness 与根 harness 双轨 | ingress-controller 等已有独立 docs/harness | 工作单元入口 | 根只索引，不吞并组件规范 |
